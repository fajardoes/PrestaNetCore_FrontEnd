========================================================
OBJETIVO FUNCIONAL
========================================================

Crear una experiencia frontend para:

1. Consultar el estado operativo del cierre diario de cartera.
2. Ejecutar el cierre diario para la fecha operativa vigente.
3. Ejecutar simulacion/dry-run del cierre diario.
4. Consultar historico de runs de cierre.
5. Consultar detalle de procesos por run.
6. Mostrar errores, advertencias, contadores y bloqueos operativos.
7. Respetar permisos del usuario autenticado.

El cierre diario de cartera ya existe en backend y opera sobre:

- fecha operativa vigente del sistema,
- dia operativo abierto/cerrado,
- periodo contable automatico,
- devengo de intereses,
- reconocimiento de cargos diferidos,
- refresco de estados de cuotas,
- calculo de mora diaria cuando existe configuracion suficiente,
- snapshots diarios,
- eventos auditables internos,
- runs y detalles auditables.

========================================================
LO QUE FRONTEND NO DEBE HACER
========================================================

Frontend NO debe:

- pedir al usuario una fecha arbitraria para ejecutar el cierre;
- asumir que puede cerrar fechas pasadas o futuras;
- avanzar automaticamente la fecha operativa;
- efectivizar pagos REGISTERED desde el cierre diario;
- liberar exposicion de canales de recaudacion desde el cierre diario;
- crear depositos bancarios automaticos;
- implementar reversa destructiva de cierres;
- inventar endpoint de compensacion;
- inventar endpoint para eventos diarios;
- inventar endpoint para snapshots diarios;
- asumir que `COMPLETED_WITH_ERRORS` es equivalente a `COMPLETED`;
- asumir que `dryRun` no deja registro: dry-run crea run, detalles y eventos de calculo, pero no aplica efectos contables ni snapshots.

La efectivizacion de pagos sigue siendo flujo administrativo separado:

- `POST /api/payments/{id}/effectivize`

La exposicion de canales se libera en pagos, no en cierre diario.

1. Consultar estado operativo

`GET /api/loans/daily-closing/status`

Permiso requerido: `loans.daily_closing.read`

Response 200:

```json
{
  "businessDate": "2026-05-17",
  "isDayOpen": true,
  "hasRunningRun": false,
```

Reglas UI:

- `hasRunningRun=true`: badge "En ejecucion"; deshabilitar ejecutar/simular/reprocesar.
- `isDayOpen=false`: badge "Dia cerrado"; deshabilitar acciones de ejecucion.
- `postingContextStatus!="OK"`: badge/alerta "Periodo contable no disponible"; deshabilitar acciones de ejecucion.
- `hasCompletedRunForBusinessDate=true`: badge "Cierre ya ejecutado"; mostrar "Reprocesar" solo con `loans.daily_closing.run`.

========================================================
MANEJO DE ERRORES HTTP
========================================================

Backend devuelve Problem Details para errores de servicio.

Manejar:

- 401: sesion expirada/no autenticado. El interceptor puede limpiar sesion.
- 403: mostrar acceso restringido.
- 400: validacion de negocio. Mostrar `detail/title`.
- 404: run o recurso no encontrado.
- 409: conflicto de estado:
  - ya existe run RUNNING,
  - ya existe cierre completado para la fecha sin `allowReprocess`,
  - dia operativo cerrado,
  - periodo contable no admite posteo automatico.
- 422: error semantico si backend lo usa.

Formato esperado:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "Ya existe un cierre completado para la fecha operativa vigente."
}
```

Mostrar preferentemente `detail`, luego `title`, luego fallback. El helper `toApiError` ya cubre esto.

========================================================

- `DateOnly` se renderiza como `YYYY-MM-DD`.
- `DateTimeOffset` se renderiza como fecha/hora local del usuario.
- `executionTimeMs`:
  - menor que 1000: `850 ms`
  - mayor o igual a 1000: segundos/minutos.
- `generatedAmount=null`: mostrar `-`.
- `loanNo=null`: mostrar `Proceso global`.
- `loanId`: no mostrar por defecto si hay `loanNo`; puede mostrarse como dato tecnico.

========================================================
CRITERIOS DE ACEPTACION FRONTEND
========================================================

- La ruta `/loans/daily-closing` existe y queda protegida por permiso `loans.daily_closing.read`.
- Las rutas `/loans/daily-closing/runs` y `/loans/daily-closing/runs/:id` existen.
- Las acciones de ejecucion solo aparecen para usuarios con `loans.daily_closing.run`.
- El usuario puede consultar status operativo del cierre.
- El usuario puede ejecutar dry-run.
- El usuario puede ejecutar cierre real.
- El usuario puede reprocesar cuando ya existe cierre para la fecha, enviando `allowReprocess=true`.
- El usuario ve claramente si hay pagos REGISTERED pendientes, sin que la UI prometa efectivizarlos.
- El usuario ve claramente si el periodo contable no permite posteo automatico.
- La UI no permite editar manualmente `businessDate`.
- La UI muestra Problem Details de backend de forma legible.
- La UI lista runs con filtros y paginacion.
- La UI muestra detalle de run con filtros y paginacion.
- La UI distingue visualmente `COMPLETED`, `COMPLETED_WITH_ERRORS`, `FAILED` y estados `DRY_RUN`.
- La UI no llama endpoints inexistentes de eventos, snapshots, reverse o compensate.
- La implementacion respeta capas: contracts en infrastructure, API/actions en core, hooks/components/pages en presentation.
